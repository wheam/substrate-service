# 02 — 长期产品化

> 前提：01 的个人版跑顺、M3 的"我真的天天在存"成立。
> 定位一句话：**一个"AI 记忆层"服务——手机上一个 App 负责收，云端一个 keeper 负责理，
> 任何 AI 通过 MCP 连上来就认识你；而你的数据永远是可带走的 markdown + git。**

## 1. 用户体验（产品的四个瞬间）

1. **接一个 AI = 半分钟**：在 Claude / ChatGPT / Cursor / 任意支持 MCP 的宿主里粘连接地址 → 标准 OAuth 授权页（"允许读取知识、投递收件箱？"）→ 完成。用户设备零安装，无 VPN、无插件。
2. **存东西 = 一步**：任何 App 里点分享 → 选本产品 → 完事。keeper 后台抓取、判断、归档，推送一条"已存 → 餐厅收藏"。
3. **收件审阅 = 心脏界面**：keeper 拿不准的（"像决定也像随想，存吗？"）、拒收的（"含疑似密钥，没入库"）都在这里，一屏处理。
4. **每个 AI 开口就认识你**：连接即下发使用守则（先查库再答、查无不编、什么信号该提议存），工具描述即路由。

## 2. 多租户架构（= Engine/Instance 分离的产品化）

```text
 用户的各个 AI ── MCP(OAuth) ──┐        ┌── API 网关（OAuth 2.1 / scopes / 限流 / 审计）
 手机 App ────── HTTPS ────────┼──────► │
 Web 控制台 ──── HTTPS ────────┘        │  keeper 工人池（无状态，按任务领活）
                                        │  每租户一个实例：markdown + git
                                        │   ├─ 静态加密、租户隔离
                                        │   └─ 可绑用户自己的 GitHub 远程（BYO remote）
                                        └── 审计日志（用户可见）
```

- **租户边界 = Engine/Instance 边界**：引擎代码全租户共享；每个租户一个实例目录（zones/宪法可在护栏内自定义）。个人版就是租户 #1，架构无需推翻。
- **BYO git remote 是核心卖点**：每个租户的实例是真 git 仓库——全历史、随时 `clone` 导出、可绑自己的 GitHub 私库持续备份。"产品死了数据不死"从口号变成勾选框，也是对黑箱记忆类产品最锋利的差异化。
- **服务与引擎的仓库关系**：`substrate`（开源，格式/治理/契约的事实源）+ `substrate-service`（产品：网关、keeper、App、控制台、计费）。open-core：开源引擎是信任背书和自托管入口，托管服务和 App 是商业化载体，二者不左右互搏。

## 3. keeper 规模化（产品的核心资产与核心成本）

**归属模型：逻辑上每个实例一个，物理上无状态工人池。**

- **逻辑上每实例一个（硬要求）**：判断装载的全是该库的东西——它的宪法/zones/分类法、它的索引（去重）、它的历史判例（用户每次纠正都攒成 few-shot）。**个性化状态存在用户自己的实例仓库里**（keeper-feedback 区，markdown+git）——导出库=连"调教好的 keeper"一起带走，这是服务端黑箱做不到的。跨租户判断互不可见（隐私 + 质量双重要求）。
- **物理上工人池（轻的做法）**：keeper 是"确定性外壳 + 按需 LLM 调用"，任务间无保温状态。一条全局队列（带 tenant_id），工人领活→装载该租户上下文→判断→在该租户实例执行→下一条。量级：1 万用户 × 30 条/天 ≈ 每秒 3–4 条，几个工人即消化；成本按条付（小模型分类 + 低置信升级），COGS 在订阅价（$8–15/月档）内成立。反例——"每人一个常驻 keeper 进程"才是重的方案：万级进程空转 + 运维万只宠物。
- **keeper 属于"库"不属于"人"**：多库用户（个人库 + 家庭共享库）= 多个 keeper 上下文，capture 路由到哪个库就按哪个库的规矩理。
- **质量体系**：全局 golden 判例集（基线回归，模型升级必跑）+ 每租户判例（个性化）。keeper 判断质量就是产品质量，01 阶段攒下的判例集是最早的护城河。

## 4. 安全与信任（公网姿态的正式版）

- **认证**：OAuth 2.1（MCP 规范路线，宿主端已是成熟惯例）；App/控制台走账号体系（passkey 优先）。
- **授权**：per-connection scopes（读 / 投递 / 按 zone）；zones 的 `privacy`/`readers` 落地为真 ACL——低信任连接拿不到 sensitive 记忆。
- **架构自带的两道界**（继承 01）：写入只进 inbox 隔离区（token 泄露 ≠ 库被写坏）；keeper 视一切内容为数据非指令，且无导出/删除类动作可被诱导。
- **审计**：每次工具调用用户可见可查——"可审计"从引擎口号变成产品功能。
- **数据**：静态加密、租户隔离、区域托管；远期 SOC2。架构上已天然免疫最大的信任坑：内容永远是可导出的开放格式，不存在"绑架式私有格式"。

## 5. 多人共享库

- zones 的 `readers`/`writers` 接到成员系统上 = 家庭/小团队共库（"我们家的餐厅清单""团队决策记录"）。
- 每个成员的各个 AI 各自连接，按成员权限读写；共享库有自己的 keeper 上下文与规矩。
- 排期原则：放在单人版被大量用户用爽之后——它引入成员管理、冲突仲裁、计费分摊等一整层复杂度。

## 6. 难点（如实列出）

1. **keeper 判断质量是生死线**：一个人的库好调，万级用户的杂乱输入（截图、语音转写、转发的转发）才是真考验。对策：判例集回归体系 + 低置信不猜转人工 + 分类边界宁窄勿宽。
2. **赛道拥挤**：mem0、Limitless、各平台自带记忆都在卷。生位必须钉死在"**agent 中立 + 用户主权**"：不绑任何一家 AI、数据可带走、维护规则可读可审计。丢了这个就泯然众人。
3. **信任成本**：托管他人最私密的数据，安全事故一次清零。加密、审计、合规是成本中心但不可省。
4. **中国/海外双区发行**：国内要可达性 + 微信/小红书生态捕获通道 + 合规；海外要 App Store + Claude/ChatGPT 连接器生态。架构同一套，发行两条线，定价与托管要早想。
5. **MCP 宿主生态的不均匀**：各宿主对 instructions/OAuth 支持程度不一 → 保留 digest 注入兜底通路，按宿主实测维护一张兼容表。

## 7. 从个人版到产品：全部是加法

| 增量 | 说明 |
|---|---|
| 账号 + OAuth 2.1 | 替换个人版的静态 token |
| 多租户化 | 实例目录 ×N + 队列带 tenant_id（01 的架构已按此形状写） |
| Web 控制台 | 收件审阅（App 已有雏形）+ 连接管理 + 审计查看 |
| App 上架 | TestFlight 自用版 → App Store（双区） |
| 计费 | 订阅 + 免费层（限捕获量） |
| BYO remote | 把 01 的"push GitHub"暴露成用户功能 |

**没有一步需要推翻 01 的代码。**

## 8. 非目标与开放问题

- 非目标（当前不设计）：浏览器插件、邮件转发入库、语音捕获、本地端侧模型。
- 开放问题：产品名 / 域名；国内主体与合规路径；免费层的滥用防护；共享库的冲突仲裁 UX；是否提供"只读公开页"分享形态。
